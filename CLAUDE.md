# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Dayleaf — a self-hosted, single-user journaling PWA deployed to the owner's NAS via Docker. Source of truth for deployment is `ghcr.io/t0n003c/dayleaf`, built automatically by `.github/workflows/docker.yml` on every push to `main` (multi-arch amd64+arm64). Pushing to main IS the release process.

## Commands

```bash
npm install && npm --prefix web install   # both dependency trees
PORT=3210 npm run dev                     # API server with --watch, data in ./data
npm --prefix web run dev                  # Vite dev server :5173, proxies /api -> :3000 (see note)
npm --prefix web run check                # TypeScript type-check (no test suite exists)
npm --prefix web run build                # production bundle -> web/dist
docker build -t dayleaf:test .            # what CI runs; verifies the full stack
```

**Port gotcha:** on this machine port 3000 is occupied by Open WebUI. Run the API on 3210+ and, if using the Vite dev server, adjust the proxy target in `web/vite.config.ts` accordingly. Stray requests to :3000 will get Open WebUI's HTML and look like bizarre API failures.

There is no unit test suite — `bash scripts/smoke.sh http://localhost:3210` is the regression gate (a curl suite against a server started with a **fresh** data dir; it runs first-time setup itself, and its final checks deliberately trip the login lockout, so run it last). AI streaming can be tested against a local mock of `POST /chat/completions` returning SSE. See the `smoke-test` and `release` skills for the full flows.

## Architecture

One Express server (`server/`) serves both the JSON API under `/api/*` and the built SPA from `web/dist` (everything non-`/api` falls through to `index.html`). One container, one volume.

- **No compile-time native dependencies is a design constraint.** The DB is the Node built-in `node:sqlite` (`server/db.js`), not better-sqlite3; password hashing is `node:crypto` scrypt. The one allowed native module is `sharp` (image pipeline) because it ships prebuilt binaries for linuxmusl x64+arm64 — the Docker build stays a plain `npm install` with no toolchain. Don't add modules that need node-gyp.
- **Image pipeline** (`server/images.js`): every upload is converted to WebP (EXIF-rotated, capped at 2000px, q82) plus a 480px thumbnail in `uploads/thumbs/`; undecodable files are kept as-is and the thumb route falls back to the original. `GET /api/files/:name?thumb=1` serves the thumbnail; grids use it, viewers use the full file. Missing thumbnails for pre-pipeline photos are backfilled in the background at boot.
- **Security middleware** (top of `server/index.js`): CSP (two hashed inline bootstrap scripts — change a script → update its hash or the browser blocks it; the journey asserts no CSP violations), nosniff/frame-deny/referrer headers, and a same-origin Origin check on state-changing `/api` requests. Cookies are `Secure` by default (`COOKIE_INSECURE=1` for plain-HTTP LAN). `trust proxy` = `TRUST_PROXY_HOPS` (default 2), and `security.js` only honors proxy IP headers from the trusted hop. The AI base URL is SSRF-guarded (`ai.js` `assertAllowed`: blocks private/loopback unless `AI_ALLOW_PRIVATE=1`). Uploads reject SVG and serve with nosniff. Container runs as non-root `node`. See SECURITY.md. Local dev/journey needs `COOKIE_INSECURE=1 AI_ALLOW_PRIVATE=1` (plain http + localhost mock provider).
- **Schema migrations** (`server/db.js`): the CREATE-IF-NOT-EXISTS block is the FROZEN v0 baseline; future schema changes are append-only entries in the `MIGRATIONS` array, run from `PRAGMA user_version` upward, each in its own transaction (fresh and existing DBs converge). Never edit the baseline or a shipped migration.
- **Backup/restore** (`server/backup.js`): `GET /api/backup` streams one self-describing JSON (tabs, entries, attachment metadata, settings, user row, and photos as base64) — chosen over zip for maximum future-proofness/zero deps. `POST /api/restore` (multipart, disk-buffered up to 1GB) transactionally REPLACES all data, rewrites photos (sanitized filenames), clears sessions, and triggers thumbnail backfill. The backup contains secrets (pass hash, TOTP, AI key) — it's the owner's to safeguard.
- **All state lives under `DATA_DIR`** (default `/data`, always resolved to an absolute path — `res.sendFile` requires it): the SQLite file, WAL files, and `uploads/` for photos. App settings (AI base URL/key/model) are rows in the `settings` table, not env vars; there is no `.env`.
- **Auth is single-user** (`server/auth.js`): scrypt password + DB-backed session cookie, optional TOTP (otplib), optional WebAuthn passkeys (`server/webauthn.js`). Both `@simplewebauthn/server` and `@simplewebauthn/browser` are pinned to **v9** — the v10+ API is incompatible (userID type, option shapes); upgrade both sides together or not at all. The WebAuthn RP ID/origin are derived per-request from `Host`/`X-Forwarded-*` headers plus Cloudflare's `cf-visitor` scheme (`trust proxy` is on), with a `PUBLIC_ORIGIN` env override — needed because Nginx Proxy Manager rewrites `X-Forwarded-Proto` to its upstream scheme. Brute-force protection lives in `server/security.js`: DB-persisted per-IP and global failure counters with cooldowns (env-tunable via `MAX_LOGIN_ATTEMPTS` etc.), a 400ms flat delay per failure, a login-activity log surfaced in Settings, and a push alert on lockout. Asking for the TOTP code (no code supplied yet) is NOT a failure — only wrong codes are. Passkey failures are logged to the activity feed but EXCLUDED from lockout counting (signatures aren't guessable; counting them would let cancelled Face ID prompts lock the owner out). When passkeys exist, the login screen auto-attempts biometric on load and reveals the password form only after that fails.
- **AI recall** (`server/ai.js`) proxies to any OpenAI-compatible `/chat/completions` with the user's own key. The server parses the provider's SSE stream and forwards **plain text chunks** (not SSE) to the client, which reads them via `fetch` + `ReadableStream` (`web/src/api.ts` `ask()`). Journal context is assembled server-side: entries filtered by tab IDs/date range, newest first, capped by char budget (`AI_MAX_CONTEXT_CHARS`, default 200k), with today's date; the `/api/ask` response sets `X-Dayleaf-Context: included/total` so the client warns when older entries didn't fit. `/api/recap` (`streamRecap`) is map-reduce: it summarizes each month independently then synthesizes a digest (lenses: recap/accomplishments/interview/mood), so a full year is covered regardless of context size; it streams progress lines, a `\f` separator, then the digest. `aiText` (non-stream helper) tolerates providers that stream despite stream:false.
- **Frontend** (`web/src/`) is React+Vite with no router: `App.tsx` switches between three views (Journal/Ask/Settings) and gates on `/api/me` (`needsSetup` → Setup, unauthed → Login). Tabs are user-defined journals; entries are intentionally **plain text only — never render markdown** (explicit product decision). PWA manifest shortcuts deep-link via `/?action=new|ask`, handled in `App.tsx`. Tabs live in a collapsible left sidebar (`components/Sidebar.tsx`; desktop icon-rail state in localStorage, mobile edge-swipe drawer driven by touch handlers in `App.tsx`) with pointer-event drag-to-reorder (PUT `/api/tabs/reorder` — registered before `/api/tabs/:id`), inline edit, and delete; `activeTab` state lives in `App.tsx`. The Journal composer is collapsed by default (a "quick-jot" pill with rotating daily prompts) and expands on tap or via the `?action=new` shortcut — inline on desktop, docked at the bottom + opening as a bottom sheet on mobile (the Ask input card docks the same way on mobile, with its dropdowns opening upward); the greeting header shows streak/days pills from `/api/stats`, and `/api/onthisday` feeds the "On this day" memories card. Entries are tap-to-edit (no Edit button; delete is an ✕); a 400ms press-and-hold starts a pointer-based drag (`beginEntryDrag` in `App.tsx`) onto a sidebar journal (`data-droptab` rows) to move the entry — works for mouse and touch, opens a closed/collapsed sidebar when the pointer nears the left edge, and a `journalRefresh` signal reloads the list after a move. The Photos view (`views/Gallery.tsx`) lists every attachment via paginated `/api/attachments` (infinite scroll with an IntersectionObserver sentinel) and opens a keyboard-navigable viewer. Endpoints taking dates accept `?today=YYYY-MM-DD` from the client because entry dates are user-local while the server may run in UTC.
- **Daily reminders** (`server/push.js`): Web Push via the `web-push` package (pure JS). VAPID keys are generated once and persisted in the `settings` table — never regenerate them, existing subscriptions would break. A 30s `setInterval` loop compares the user's local time (client-supplied IANA `tz`, formatted with `Intl`) against the configured reminder time, claims the day via `reminder_last_sent` *before* sending, and skips days that already have an entry. The same loop sends the optional "on this day" flashback push at 09:00 local (`memories_enabled`/`memories_last_sent`; date math shared with the API route via `server/memories.js`). Push handlers live in `web/public/sw.js` — bump its `CACHE` version whenever the service worker changes.
- **PWA bits** live in `web/public/`: hand-rolled `sw.js` (stale-while-revalidate navigations for INSTANT paint = no launch flash; the bg revalidate also precaches the assets the fresh shell references, and old assets are NEVER purged (stable cache name), so a cached shell can always resolve its bundle = no blank-after-update; manifest is network-first so splash/theme changes propagate; never caches `/api`. The cache name (`dayleaf-app`) is intentionally STABLE — do NOT version-bump it; the old purge-on-activate is what caused the blank-after-update bug, so it now only cleans up legacy `dayleaf-v*` caches once), `manifest.webmanifest`, icons generated from `icons/icon.svg`. Anti-flash boot path: `index.html` applies the theme + background via inline script/style BEFORE first paint, and `App` shows a `.boot-splash` while `/api/me` resolves — don't reintroduce `return null` there.
- **Motion system**: leaf theme throughout — falling-leaf + WebGL dappled-light (`components/LeafLight.tsx`, seasonal palettes) auth backdrop, save leaf-burst + streak milestones (`components/celebrate.ts`), staggered entrances, rAF-driven gestures (drawer edge-swipe in `App.tsx`, photo-viewer swipe/pinch/double-tap in `Gallery.tsx`, sheet drag-dismiss in `Journal.tsx`). All respect prefers-reduced-motion. Two CSS traps documented inline in styles.css: transforms on `.view-wrap` create a containing block that misplaces the fixed docks, and filled opacity animations leave a stacking context that traps overlays.

## Conventions

- Dates: `entry_date` is a local-time `YYYY-MM-DD` string; the frontend produces it with `toLocaleDateString('sv')`. Timestamps in the DB are UTC `datetime('now')`.
- API errors are always `{ error: string }` with an appropriate status; the client surfaces `err.message` directly to the user.
- Never use `window.confirm/alert/prompt` — they show the site origin ("dayleaf.example.com says"). Use `appConfirm`/`appAlert`/`appPrompt` from `web/src/components/dialog.tsx` (the `DialogHost` is mounted in `App.tsx`).
- Photo files get random hex names in `uploads/`; the DB row in `attachments` is the source of truth, and deletion paths (entry, tab, attachment) must unlink files too.
